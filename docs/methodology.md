# 무결성 렌즈 5문항 — 방법론의 알맹이

> 판단 기준은 "잘 되는가"가 아니라 **"오류 없이 + 그것을 교차검증할 방법이 있는가"** 이다.
> **파이프라인은 최약 단계로 수렴한다** — 한 단계라도 검증이 없으면 전체가 미검증이다.

행정문서를 AI가 읽게 만드는 파이프라인은 다섯 단계를 지난다: 수집 → 변환 → 비식별 → 서빙 → (이 모든
것의) 교차검증. 각 단계에 던지는 질문과, 이 프로젝트가 실제로 배치한 검증 수단은 다음과 같다.

## 1. 수집 — 빠짐없이 가져왔는가, 빠진 것을 어떻게 아는가

크롤러가 "돌았다"와 "다 가져왔다"는 다른 명제다. 완전성은 선언이 아니라 대조로 확인한다:

- **선언 총건수 대조**: 게시판이 스스로 선언하는 총 게시물 수와 수집 건수를 대조
- **순번 연속성 검사**: 게시물 순번의 구멍을 탐지(중간 유실 검출)
- **시작 경계 정책 주입**: "여기부터 있어야 한다"는 기대를 명시해 조용한 앞구간 유실 차단
- **실패 다운로드 게이트**: 서버가 에러 페이지를 200으로 주는 경우를 본문 검사로 걸러냄

## 2. 변환 — 오류 없이 변환했는가, 손실을 어떻게 찾는가

HWP·PDF → 마크다운 변환은 조용히 실패한다(텍스트가 비거나, 표가 뭉개지거나). 대응:

- **차등 하네스**: 서로 다른 변환기 2계통 + 원문 정답지의 3자 대조로 변환 손실을 탐지
- **0-silent 마커**: 손실이 나면 조용히 버리지 않고 문서에 마커를 남긴다 — 서빙 단계가
  `needs_review`로 정직하게 노출
- **품질 채점**: 변환 산출물마다 품질 신호를 채점해 저품질 문서를 식별

## 3. 비식별 — 양방향 모두 오류다

개인정보 마스킹은 한 방향 문제가 아니다. **과소 마스킹 = 유출**이고, **과잉 마스킹 = 행정데이터
손상**이다(전화번호를 지우려다 예산 수치를 지우면 그것도 오류). 대응:

- 스캔 게이트 + 체크섬으로 마스킹 전후 무결성 확인
- **양방향 보존 골든**: "지워야 할 것이 지워졌다"와 "지우지 말아야 할 것이 남았다"를 둘 다 검증

## 4. 서빙 — 답변 3원칙을 계약으로

모든 도구 응답의 계약(개별 도구가 아니라 응답 검사기가 스위프로 강제):

1. **모든 사실에 근거 문서 명시** — source·URL·기관 인용
2. **근거 기반 vs 추론 구분 표시**
3. **근거 없으면 "확인되지 않습니다"** — `grounded=False` 거절, 추측으로 메꾸지 않음

여기에 **침묵 절단 계약**이 더해진다: 목록을 자를 때는 반드시 ①잘렸음을 보이게 ②이어갈 방법을
안내하게 ③파생 수치는 절단과 무관하게 전수로 계산하게. "상위 10건"이 조용히 전체인 척하는 것을
기계 검사로 차단한다.

## 5. 교차검증 — 검증 수단 자체를 검증한다

앞 단계의 검증기들이 실제로 결함을 잡는지 누가 보증하는가. 두 규율:

- **fail-first 골든 채택 규율**: 골든 테스트는 **"옛 코드에서 실패함을 먼저 확인한 것만"** 채택한다.
  통과만 하는 골든은 아무것도 안 잡는 골든이다.
- **탐지기 자가검증**: 결함 탐지기는 기지 결함을 주입해 잡아내는 것을 확인한 뒤에만 가동한다.

상시 가동 중인 교차검증 계층(주간 자동 스캔):

| 탐지기 | 무엇을 교차하나 |
|---|---|
| 쿼리로그 결함 신호 | 실사용 질의에서 거절·오류 패턴 추출 |
| 트리합 재검증 | 예산 트리의 부모=자식합 불변식 전수 재검산 |
| 재정 대조 | 문서에서 파싱한 예산 총액 ↔ 지방재정365 공식 수치 대조 |
| 계약 퍼저 | 무작위 인자로 도구를 두들겨 응답 계약 위반 탐지 |
| 역생성 문항 | 서빙 데이터에서 역으로 생성한 160문항으로 검색 품질 상시 채점 |

실증 한 가지: 재정 대조 탐지기는 "예산 파싱이 4개 연도에서 과소하다"는 오랜 가설의 실원인이
파싱이 아니라 서빙 단계의 문서 충돌 탈락임을 밝혀냈고, 수정 후 15개 연도 전수가 지방재정365와
원 단위까지 일치함을 확인했다 → [results.md](results.md)

## 정직성은 운영에도 적용된다

- 레이트 리밋 429 응답은 한도·재시도 시점을 정직하게 안내한다
- 검증에 걸린 저품질 문서는 숨기지 않고 `needs_review`로 표시된 채 서빙된다
- 폐지 추정 자치법규는 현행처럼 서빙하지 않고 정직 안내 + 원문 링크로 유도한다
- 서비스 자가진단(워치독)은 "발동 0회"를 성공지표로 삼는다 — 안전망의 성공은 쓰이지 않는 것

맛보기 — 레이트 리밋의 fail-first 골든(실코드 발췌, 한도 없는 옛 코드가 실패함을 먼저 실증):

```python
# 골든 0 — 옛 코드(무게이트) 실패 실증: 한도 없는 앱은 25연속 전부 200 = 이 게이트가 잡는 결함
with TestClient(bare) as c:
    assert all(c.get("/mcp").status_code == 200 for _ in range(25)), "bare 앱 전제 붕괴"

lim = RateLimiter(per_min=20, per_day=500, clock=lambda: fake[0])   # 주입 시계 — 결정론 검증
with TestClient(RateLimitMiddleware(bare, lim)) as c:
    # 골든 1 — 분당 한도: 20 허용, 21번째 429(+Retry-After·정직 안내 body)
    assert all(c.get("/mcp").status_code == 200 for _ in range(20)), "정상 트래픽 오탐"
    r = c.get("/mcp")
    assert r.status_code == 429 and "retry-after" in r.headers
    # 골든 2 — 61초 경과 → 회복(영구 차단 아님)
    fake[0] += 61
    assert c.get("/mcp").status_code == 200, "1분 창 회복 실패"
```
